## 1. Executive summary

Three live P1s, all newly introduced or newly exposed by the v1.8.0 globe-default release:

1. **GL-1 — a `patch-package` patch makes the default home screen fetch 1024 satellite tiles instead of 16.** A 64× increase in requests and bytes on every cold start, for every user, because v1.8.0 made the globe the default view.
2. **ST-4 — one transient settings *read* failure permanently erases the user's entire profile.** Proven with a runnable repro: a single rejected `Preferences.get` causes the provider to write defaults over the stored blob.
3. **PM-1 — an unthrottled render/storage storm fires at every prayer boundary, 6× a day.** Proven: during the final second before each prayer, an effect loop spins until the wall clock crosses the target.

Separately, **the iOS target is not shippable** (§4). `ios/` has only ever been touched in the initial commit, has zero privacy usage descriptions (a hard crash plus an App Store rejection), and its compass cannot work at all. The README advertises "Android and iOS", so this is a documentation-vs-reality gap as much as a code gap.

And **the shipped privacy policy is materially inaccurate** (**DOC-1**): it states that reverse geocoding "is the only external network request the app makes", while the app in fact contacts six third-party hosts — including Esri satellite tiles on *every cold start* now that the globe is the default view, and Google Fonts on every launch. The same claim is repeated in the Play Store listing copy.

The single most common *class* of bug found is **a fix applied at one layer but not at its consumers** — A-6 was fixed in `prayerTrackingService` but not in `Dashboard` (ST-1); A-1 was fixed for `currentPrayer`/`nextPrayer` but not for the `prayers` array (PM-3, GL-3); A-11 was fixed with a resync effect that then introduced its own defect (ST-6); C-2 was fixed in `useQibla` but the identical race survives in `useTimezone` (MH-3) and in `useQibla`'s unmount path (LQ-9).

## 2. P1 — fix before the next release

### GL-1 — The tile-threshold patch makes the default home view fetch 1024 Esri tiles instead of 16
**CONFIRMED (independently recomputed) · ✅ FIXED** · `patches/three-slippy-map-globe+1.0.6.patch` → applied at `node_modules/three-slippy-map-globe/dist/three-slippy-map-globe.mjs:324-326`, consumed at `:476-479` · app side `src/components/three/homeGlobe.ts:33` (`HOME_ALTITUDE = 2.5`), `:658-669` (`enableTiles`)

The patch rewrites the tile-level threshold table with no explanatory comment:

```js
- return 8 / Math.pow(2, idx);
+ return [100, 90, 80, 70, 60, 0.2, 0.1, 0.06][idx] || 0.0001;
```

Level selection is `thresholds.findIndex(t => t && t <= cameraDistance)`. The app never sets `globeTileEngineMaxLevel`/`MinLevel`, so the library defaults apply (`minLevel = 0`, `maxLevel = 17`, `three-slippy-map-globe.mjs:304-306`) — nothing clamps the result.

I recomputed the tile counts independently using the library's own `genTilesCoords`:

| camera altitude | upstream | patched |
|---|---|---|
| **2.5 — `HOME_ALTITUDE`, the default framing** | level 2 → **16 tiles** | level 5 → **1024 tiles** |
| 1.0 | level 3 → 64 | level 5 → 1024 |
| 0.5 | level 4 → 256 | level 5 → 1024 |
| 0.06 — `MIN_ALTITUDE`, deepest pinch | level 8 → 65536 | level 7 → **16384** |

**Root cause, precisely:** the flat `100/90/80/70/60` prefix puts levels 0–4 out of reach at *any* altitude the app permits (`MAX_DISTANCE / GLOBE_RADIUS = 35`, still below 60). The engine therefore pins to level 5 for everything from the home framing down to altitude 0.2.

**Note the patch is not simply wrong** — at the deep-zoom end it *reduces* the count 4× (16384 vs 65536). It was evidently written to tame that explosion and overshot at the other end. The fix is a monotonic ramp, not a revert.

**Failure scenario:** every cold start of the now-default home screen fires ~1000 requests at `server.arcgisonline.com` for roughly 14 MB of JPEG. Three consequences stack:

- **The loader cannot work as designed.** `enableTiles()` arms `fireSurfaceReady()` at `FIRST_TILES_MAX_WAIT_MS = 3000` (`homeGlobe.ts:665`), so the Basmala prelude lifts at 3 s revealing a partly-filled mosaic. The real completion signal is `DefaultLoadingManager.onLoad` (`:484-495`), which three.js only fires once *all* ~1000 tiles land. The render loop meanwhile parks at `INITIAL_SETTLE_MS = 4000` (`:452`), so between 4 s and the end of the storm **nothing redraws and the globe freezes mid-fill**.
- **GPU/CPU:** ~1000 tile meshes, each with its own material and 256² texture (SUSPECTED magnitude — cannot render in jsdom). Frustum culling does not occlude the back hemisphere.
- **Esri's free endpoint can 429** under a 1000-request burst, leaving permanent holes in the mosaic.

Also: `TILE_RETAIN_MAX = 120` retention only covers levels *above* the current one, so zooming back **out** to the default re-fetches all 1024.

**Fix direction:** restore a monotonic ramp keyed to the altitudes the app actually uses (so level 4–5 is reached around altitude 1.0–2.5 rather than 0.2), or leave upstream thresholds alone and set `globeTileEngineMaxLevel` explicitly. Either way re-size `INITIAL_SETTLE_MS`/`FIRST_TILES_MAX_WAIT_MS` against the real tile count, and key the loader off tile *progress* rather than `onLoad`.

### ST-4 — A transient settings **read** failure is immediately followed by a defaults **write**, erasing the user's profile
**CONFIRMED (reproduced) · ✅ FIXED** · `src/context/SettingsContext.tsx:117-123` (save effect), `:125-201` (`loadSettings`)

```js
useEffect(() => {
  if (!isLoading) { saveSettings(settings); }
}, [settings, isLoading]);
```

`loadSettings`'s `catch` (`:196`) logs without calling `setSettings`; `finally` (`:198`) flips `isLoading` to false. Because `isLoading` is a dependency of the save effect, that flip re-runs it with `settings` still at `defaultSettings` — and `!isLoading` is now true, so **the defaults are written over the stored blob**. The corrupt-JSON path (`JSON.parse` at `:129`, inside the same `try`) lands here too.

My repro — mock one rejected `Preferences.get` against a device holding a real profile:

```
SET_CALLS: 1        WRITTEN_KEY: ontime_settings
calculationMethod: NorthAmerica   (stored was Egyptian)
homeView:          globe          (stored was list)
previousLocations: []             (stored had 1 saved city)
athan.downloadedAthans: []        (stored had 1 downloaded athan)
control (successful read) -> calculationMethod: Egyptian   ✓ no clobber
```

**Failure scenario:** one transient bridge failure on cold start — a genuine Capacitor race, or a `SharedPreferences` IOException — permanently destroys the calculation method, Asr madhab, saved locations, notification preferences, theme, home-view choice and the downloaded-athan registry. The athan MP3s remain on disk but are now orphaned and invisible. Nothing is logged that the user would see.

**Fix direction:** distinguish *read failed* from *no data*. A `loadedOk` flag gating the save effect is the minimal fix. Note `settings-persistence.test.tsx` currently pins the corrupt-JSON case as "falls back to defaults", so that test must be updated deliberately — falling back **in memory** is right, overwriting **on disk** is not.

### PM-1 — An unthrottled render/storage storm at every prayer boundary
**CONFIRMED (reproduced) · ✅ FIXED** · `src/hooks/usePrayerTimes.ts:45-64` · `src/services/prayerService.ts:172-191` · amplified at `src/components/PrayerTable.tsx:73-80` and `IslamicPrayerTable.tsx:77-84`

`getTimeUntil` floors to whole seconds, so for the **entire final second before a prayer** it reports `totalSeconds: 0` while the target is still in the future:

```js
if (!Number.isFinite(diff) || diff <= 0) return { …, totalSeconds: 0 };
const totalSeconds = Math.floor(diff / 1000);   // diff ∈ (0,1000) → 0
```

`usePrayerTimes.ts:55-56` treats that as "countdown finished":

```js
if (timeUntil.totalSeconds <= 0) { setDate(new Date()); }
```

I verified the two facts that close the loop:

```
[PM1] 500ms before target -> {"hours":0,"minutes":0,"seconds":0,"totalSeconds":0}
[PM1] recompute for the identical instant: same timestamp? true | same object identity? FALSE
[PM1] prayers array identity? FALSE
[PM1] control, 60s before target -> totalSeconds = 60   ✓ no trigger
```

So: `setDate(new Date())` → new `Date` identity → the `prayerData` `useMemo` recomputes → `calculatePrayerTimes` returns a **new `nextPrayerTime` object for the same instant** → the countdown effect's sole dependency (`:64`, `[prayerData.nextPrayerTime]`) changes → the effect tears down, re-registers and calls `updateCountdown()` *synchronously* → `totalSeconds` is still 0 → `setDate` again. Nothing inside the cycle can terminate it. React does not catch this (its "too many re-renders" guard covers render-phase `setState`, not effect-phase).

The loop ends only when the wall clock passes the target, at which point `nextPrayer()` advances to the following prayer. **The window is therefore bounded to roughly one second — but it is guaranteed, 6× a day**, because the 1 Hz tick always lands somewhere inside `[T−1000ms, T)`.

**Why it costs more than one second of work:** each iteration also produces a new `prayers` array identity, which re-fires the A-13 tracking-reload effect in both tables (`PrayerTable.tsx:80`, `IslamicPrayerTable.tsx:84`) → 5 × `getPrayerStatus` → `loadTrackingData` → a `Preferences.get` native-bridge read plus a full `JSON.parse` of the 30-day tracking blob, **per iteration**. The deep dive measured ~1660 iterations/second on desktop (~2000 queued storage reads). Those bridge calls are asynchronous and drain *after* the loop ends, so the visible jank outlasts it. Every iteration also re-renders the non-memoized `HomeGlobeScreen` (MH-8) and re-runs `view.update()`.

**Failure scenario:** at exactly the moment the athan notification fires and the user opens the app, the main thread is saturated for a second or more on a low-end handset; the hero countdown reads `00:00:00` throughout.

**Fix direction:** gate the refresh on the raw millisecond diff (`targetTime.getTime() - Date.now() <= 0`) rather than the floored `totalSeconds`; key the effect on `nextPrayerTime.getTime()` instead of object identity; and make the tables' status reload depend on a day-key string rather than the `prayers` array identity.

**Why it matters.** Every one of these requests carries the user's IP address. Google Fonts served from the CDN is a well-established personal-data-transfer concern under GDPR (it is the subject of court rulings and DPA guidance in several EU states), and the Esri tile requests additionally reveal the geography the user is viewing. `store-listing.md:29` repeats the same claim in user-facing copy — "The only network request is to display your city name using OpenStreetMap" — so the inaccuracy reaches the Play Store listing, not just the policy page.

**Compounding:** the v1.8.0 release notes (`docs/releases/2026-09-05-v1.8.0.md`) instruct "Glance at the Data safety form… no change is expected", but v1.8.0 is precisely the release that made the Esri-tile globe the default home view for every user. The policy's own "No accounts, no analytics, no ads" and on-device-storage claims appear accurate; the defect is specifically the *exhaustiveness* of the network disclosure.

**Fix direction:** list all six services in the Third-Party Services section with what is sent and why; drop "the only external network request"; correct `store-listing.md:29`; and re-check the Play Console Data safety form. Self-hosting the fonts (GL-8) and the moon texture (GL-5) removes two of the four outright, which is the cleaner fix.

#### DOC-1a — what actually leaves the device, destination by destination

**Attached to every single request** (WebView or native HTTP stack): the device's **IP address** — which is itself a city-level approximation of location — the User-Agent (device model, Android and WebView versions; a fingerprinting surface), `Accept`/`Accept-Language` (revealing locale), and on Android a `Referer` of `https://localhost/` (from `androidScheme: 'https'`), which identifies the app but not the user.

**No cookies are attached to any cross-origin request.** There is no `credentials`, `crossOrigin` or `withCredentials` setting anywhere in `src/`, and three.js's `ImageLoader` sets `crossOrigin = 'anonymous'`, which means "CORS request, no credentials". No auth tokens, no device identifier, no account.

**On Esri specifically** — the question worth answering precisely, because it is by far the highest-volume destination. It never receives coordinates. But two indirect channels exist:

1. **IP address** geolocates to roughly city level by itself, as it does for every destination above.
2. **The tile indices reveal the viewed region**, because the camera is centred on the user's location. At the default home framing the whole earth is 16 tiles, so nothing is revealed. After "My location" (level 4, ~1000 km per tile) and at deeper zoom (level 7, ~78 km per tile), the requested set narrows to the user's own area. So Esri can infer *where the user is looking* to roughly tile granularity — which, for a globe that opens centred on you, is approximately where you are.

Before the GL-1 fix this was ~1000 tile requests per cold start; after it, ~16 at the default framing.

**Two further accuracy notes on the current policy text.** It says location is sent to Nominatim "solely to convert your coordinates into a human-readable location name" — true for that request, but the OSM **embed iframes** send the same coordinates again (plus the home base) for a different purpose, and that is not mentioned. And the `headers: {'User-Agent': 'OnTime Prayer App'}` at `LocationContext.tsx:122-124` is a **no-op** — `User-Agent` is a Fetch forbidden header name, so the browser/WebView default is sent instead. Nominatim's usage policy asks for a valid identifying User-Agent and ≤1 request/second; the app currently provides neither an identifying UA nor any rate limit or contact detail, which is a **terms-of-service risk** independent of privacy.

**What never leaves the device** (verified by reading every persistence path): prayer tracking history, all settings (calculation method, madhab, themes, notification preferences, downloaded-athan registry), the travel home base, saved and previous locations, and onboarding state — all `@capacitor/preferences`, i.e. SharedPreferences. There is **no analytics, no crash reporting, no telemetry, no accounts and no ads SDK** anywhere (`package.json`, `src/`, `android/app/build.gradle` and `index.html` all checked). All prayer, qibla and solar math runs locally through `adhan`.

**Direct answer to "is location shared?"** Yes — in exactly three places: Nominatim (exact, on GPS use), the two OSM embed iframes (exact, including the home base, rendered automatically), and the `geo:` handoff (exact, user-initiated). Esri, Google Fonts, threejs.org and assabile never receive coordinates, but all four receive the device IP address, and Esri can additionally infer the viewed region from tile indices.

**The cheapest large reduction:** self-hosting the fonts (GL-8) and the moon texture (GL-5) removes two of the four undisclosed third parties entirely, and both are already recommended fixes for offline resilience. Lazy-rendering the OSM embed iframes only on an explicit tap — rather than whenever the panel opens — would remove the largest remaining undisclosed location disclosure.

## 4. iOS release blockers

**Framing:** `ios/` was last touched in the **initial commit** (`24df4c8`) and there are no App Store release notes anywhere in `docs/` — every shipped artifact is an Android `.aab` with Play Console instructions. So these are **not live bugs for today's users**; they are hard blockers for the iOS target that `README.md:3` advertises ("for Android and iOS") and that `npm run build:ios` claims to support. Either fix them or correct the README.

### LQ-2 — `Info.plist` has zero privacy usage descriptions → crash on onboarding + App Store rejection
**CONFIRMED** · `ios/App/App/Info.plist` (read in full); `grep -rn "UsageDescription" ios/` → **no matches**

The plist contains only `CAPACITOR_DEBUG`, the `CFBundle*` keys, `LSRequiresIPhoneOS`, the launch storyboard, `UIRequiredDeviceCapabilities`, orientation lists and `UIViewControllerBasedStatusBarAppearance`. There is **no `NSLocationWhenInUseUsageDescription`** and **no `NSLocationAlwaysAndWhenInUseUsageDescription`**, both of which `@capacitor/geolocation` documents as required by Apple.

`OnboardingScreen.tsx:53-55` calls `Geolocation.checkPermissions()` / `requestPermissions()` as the **second step of onboarding for every new user**. On iOS, touching CoreLocation without a purpose string terminates the app. Independently, App Store Connect rejects the binary at upload.

Also stale: `UIRequiredDeviceCapabilities` = `armv7`, unsupported since iOS 11.

### LQ-1 — iOS has no working compass at all
**CONFIRMED** · `node_modules/@capacitor/motion/dist/esm/index.js`, `web.js`; `src/hooks/useQibla.ts:104-133`; `useQiblaHeading.ts:38-46`; `ios/App/App/Info.plist`

`@capacitor/motion@8` ships **no native code** — `find` returns no `.swift`/`.java`/`.kt`, and the plugin maps `android:`, `ios:` **and** `web:` all to `MotionWeb`, which merely does `registerWindowListener('deviceorientation', 'orientation')`. On iOS 13+ WKWebView requires `DeviceOrientationEvent.requestPermission()` **from a user gesture**; `grep -rn "requestPermission" src/` shows no such call anywhere, and `startListening()` is invoked from a `useEffect`, never a tap. There is also no `NSMotionUsageDescription`, so even a correct request would be denied.

Result for every iOS user: the dial sits frozen, `accuracy` stays 0 → `calibrated` false → `QiblaHeading.tsx:86` reads "Wave the phone in a figure eight to calibrate" **forever**, while `error` stays `null` so the "no compass sensor" fallback never shows. Nothing tells the user the feature is dead. (And once events *do* flow, LQ-8 means the fallback heading is not north-referenced.)

### NT-4 — `sound: sound || 'default'` names an iOS sound that does not exist
**CONFIRMED (code) / SUSPECTED (audible outcome)** · `notificationService.ts:212,232`; `LocalNotificationsPlugin.swift:262-264`

Every notification carries `sound: sound || 'default'`, never omitted. iOS does `UNNotificationSound(named: UNNotificationSoundName(sound))` — a *named* sound, and there is no `default` file in the bundle (verified: no `.wav`/`.mp3`/`.caf` anywhere under `ios/`, no audio references in `project.pbxproj`). A named-but-missing sound does not fall back to `UNNotificationSound.default`. Separately, `makeNotificationContent` never reads `channelId`, so **the entire athan-channel mechanism is inert on iOS**.

### NT-6 (iOS half) — select and preview silently fail
See §3.3. Download works via `Filesystem`; selection and preview both die on the missing native plugin.

## Appendix — method and confidence

Five deep-dive agents worked disjoint subsystems in parallel; a sixth cross-cutting pass (mine) covered the timezone matrix, build/bundle, secrets, service worker, App wiring, a repo-wide timer/listener sweep, and the runtime-host enumeration that produced **DOC-1**/**DOC-2**. **No finding was accepted on an agent's word** — each was re-verified by reading the cited source, and the load-bearing ones were reproduced with throwaway vitest files that were deleted afterwards (`git status --porcelain` shows only this document; `tsc -b` clean; 231/231 tests pass).

Independent corroboration is noted where it happened: the unbounded `sw.js` cache was found separately by three lanes (**MH-4 / GL-14 / ST-11**), and the travel-prompt master-toggle bypass by two (**MH-1 / NT-8**).

Two hypotheses of my own were rejected by verification and are recorded in §7 rather than reported as bugs — most notably a would-be P1 "athan files are written to a different directory than they are read from", which collapsed once `Directory.External` was traced to `getExternalFilesDir(null)`. Three agent severities were adjusted: **NT-1** P1→P2 (the trigger is conditional, not guaranteed), **LQ-4/PM-5** "lower impact"→P2 (measurement shows up to 24 h of a religiously-defined allowance silently dropped, in every timezone), **LQ-6** "search-quality only"→P2 (24% of two-letter queries are affected and a wrong city can become the travel home base). **MH-2** was withdrawn entirely. Two prior-log ratings were *overturned upward*: the CitySearch early exit and the Jumu'ah ID collision were both written off as cosmetic, and both are reachable.


Confidence caveats worth stating plainly:
- **jsdom has no WebGL context**, so all GPU/visual claims (GL-1's draw-call and texture-memory magnitude, GL-13's z-fighting) are computed or reasoned, not rendered. GL-1's *tile count* is independently confirmed arithmetic; its *rendering cost* is not.
- **No physical device was used.** Android and iOS platform behaviour (NT-2's 64-request cap, NT-4's named-sound outcome, NT-14's SystemUI read grant, LQ-1/LQ-2's crash and rejection, NT-19's post-reboot burst, NT-21's Play policy) is reasoned from plugin sources, manifests and platform documentation. Each is labelled CONFIRMED or SUSPECTED accordingly. NT-14 and NT-2 are the two most worth a device check.
- **LQ-7's exact reported permission state** depends on Capacitor's Android implementation of the combined `location` alias. The finding holds regardless: `coarseLocation` is never read anywhere, so a coarse-only grant is never honoured.
